# Deployment — Supabase + Vercel

Three steps: apply the database, create your account, deploy the frontend.
Nothing here needs the service-role key; the app runs entirely on the anon
key with RLS as the security boundary.

## 1. Database (Supabase)

In your project's **Dashboard → SQL Editor**:

1. Paste and run the whole of **`supabase/setup.sql`** (all migrations + the
   seed in one file — fresh projects only; it is generated by
   `scripts/build-setup-sql.sh`, don't edit it by hand).
2. *(Optional but recommended for a first look)* paste and run
   **`supabase/mock_data.sql`** — but only **after** step 2 below, because it
   needs your user to exist. It loads Contractor One/Two/Three with six
   audits across 2026 (an improving contractor, a declining one, a new one),
   NCs across the whole classification taxonomy, and corrective actions in
   every state — so every dashboard, chart, and the follow-up queue is
   populated on first login. It also promotes the earliest-created user to
   admin. Safe to re-run. **Delete these contractors before entering real
   audit data.**

If you prefer the CLI instead of the dashboard:
`supabase link --project-ref <your-ref> && supabase db push` applies
`supabase/migrations/`, then run the seed and mock data via the SQL editor
or `psql`.

## 2. Your account

**Dashboard → Authentication → Users → Add user** (email + password,
"Auto confirm user"). Then run `mock_data.sql` (step 1.2) — it makes that
first user an admin. Without mock data, promote yourself manually in the SQL
editor:

```sql
update public.profiles set role = 'admin'
where id = (select id from auth.users where email = 'you@example.com');
```

(The profile row is created automatically by trigger; new users default to
the read-only `viewer` role until an admin promotes them — after the first
admin exists, do this from the app under **Admin → Users**.)

## 3. Frontend (Vercel)

1. **Add New Project → Import** this GitHub repository. Framework preset:
   Next.js — no other build settings needed.
2. Set two environment variables (values from Supabase **Project Settings →
   API**, same as `.env.example`):
   - `NEXT_PUBLIC_SUPABASE_URL` = `https://<your-ref>.supabase.co`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` = the anon/public key
3. Deploy, open the URL, sign in with the account from step 2.

The anon key is designed to be public; what each signed-in user can see and
do is decided entirely by the RLS policies (`0003_rls.sql`). Never put the
service-role key in Vercel env vars — the app doesn't use it.

## Local development against the same project

```bash
cp .env.example .env.local   # fill in the same two values
npm install && npm run dev
```

## Verifying a deployment

- Signed out, every route redirects to `/login`.
- After sign-in with mock data loaded: the Overview shows a program average
  around 76.8%, six finalized audits, three contractors, nine open or
  in-progress corrective actions; Contractor One's drill-down shows the 58 → 75 → 91
  trend; the Actions page lists the open items.
- `curl -s "https://<ref>.supabase.co/rest/v1/contractors?select=code" -H "apikey: <anon>"`
  returns `[]` (not an error): the table exists and RLS blocks anonymous
  reads — exactly right.
